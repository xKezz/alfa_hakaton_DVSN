## 1. Область применения

Подсистема предназначена для расчёта финансового профиля компании, оценки соответствия её параметров доступным кредитным продуктам и формирования результата для последующей обработки клиентским приложением.

Основные функции:

- получение карточки компании и финансовой отчётности через API/БД;
- расчёт отраслевого, операционного и финансовых блоков;
- нормализация финансовых данных, в том числе введённых вручную;
- фильтрация кредитных продуктов по параметрам заявки;
- расчёт факторов и итогового балла по продукту;
- определение попадания результата в пороговую зону для дополнительной проверки.

## 2. Нормативные и методические основания

### 2.1. Оформление

Структура документа ориентирована на ГОСТ 7.32–2017: титульная часть, аннотация, содержание, нумерованные разделы и приложения.

### 2.2. Методология АКРА

Теоретическая основа — документ АКРА «Методология присвоения кредитных рейтингов нефинансовым компаниям по национальной шкале для Российской Федерации» от 17 февраля 2023 года.

В методологии рассматриваются:

- отраслевой риск-профиль;
- операционный риск-профиль;
- финансовый риск-профиль, включающий размер, рентабельность, долговую нагрузку и обслуживание долга, ликвидность и денежный поток;
- аналитические корректировки и сравнение с группой сопоставимых компаний.

В реализованной системе использованы концептуально близкие группы факторов и взвешенное агрегирование. Полное воспроизведение методологии АКРА отсутствует: в частности, код не реализует весь анализ корпоративного управления, географической диверсификации, прогнозирование денежных потоков, полный набор аналитических корректировок и официальную процедуру присвоения рейтинга.

**Важно:** `fin_score` — внутренний балл системы, а не ОСК или официальный кредитный рейтинг АКРА. Методология АКРА используется как теоретическое основание, но это не означает, что каждый коэффициент из `weight.json` напрямую взят из таблиц АКРА.

## 4. Архитектура и поток обработки

### 4.1. Финансовый скоринг

Компонент `Financial_Risk_Score` получает карточку компании, финансовую отчётность и отраслевые процентили. Затем рассчитывает блоки:

1. `industry` — отраслевой риск;
2. `market_position` — рыночная позиция;
3. `business_profile` — бизнес-профиль;
4. `size` — размер компании;
5. `profitability` — рентабельность;
6. `debt_load` — долговая нагрузка;
7. `debt_service` — обслуживание долга;
8. `liquidity` — ликвидность;
9. `cash_flow` — денежный поток.

Результат включает итоговый балл, оценки блоков, использованные веса и сведения о качестве данных.

### 4.2. Скоринг кредитного продукта

Компонент `Credit_category` подготавливает клиентские данные, получает каталог кредитных продуктов, проверяет обязательные условия (статус бизнеса, цель, сумма, срок), рассчитывает балл по каждому подходящему продукту и формирует результат.

### 4.3. Зависимости

| Компонент              | Назначение                                                    |
| ---------------------- | ------------------------------------------------------------- |
| `config.py`            | Пороги, справочники, веса продуктового скоринга и имена полей |
| `weight.json`          | Веса финансовой модели и отраслевые группы                    |
| `FNSApi`               | Получение сведений о компании и финансовой отчётности         |
| `InternalApi`          | Каталог продуктов, последний отчётный год и процентили        |
| `credit_risk_score.py` | Финансовый скоринг                                            |
| `credit_category.py`   | Фильтрация продуктов и продуктовый скоринг                    |

## 8. Математическая модель

### 8.1. Нормализация показателей

Для показателя, у которого большее значение означает лучший результат, используется линейное масштабирование:

$f(x;a,b)=\min\left(1,\max\left(0,\frac{x-a}{b-a}\right)\right)$

Для показателей, у которых меньшее значение лучше, используются обратные границы. Значения за границами диапазона ограничиваются интервалом `[0; 1]`.

Для выручки, активов и капитала применяется натуральный логарифм. В качестве границ используются процентили `P5` и `P95`. Для рыночной позиции используются отраслевые процентили, для размера — процентили датасета.

### 8.2. Объединение показателей и блоков

Для доступных показателей блока:

$S_{\text{block}} = \frac{\sum_i w_i S_i}{\sum_i w_i}]$

Недоступные показатели исключаются, веса оставшихся компонентов нормируются.

Итоговая оценка рассчитывается по доступным блокам:

$S_{\text{total}} = \frac{\sum_j W_j S_j}{\sum_j W_j}$

Итоговый балл:

${fin\_score} = \operatorname{round}(1000 \cdot S_{\text{total}})$

Если данных недостаточно для расчёта итоговой оценки, балл не формируется.

### 8.3. Состав финансовых блоков

| Блок | Показатели |
|---|---|
| `market_position` | `ln(revenue)`, `net_profit / revenue` |
| `business_profile` | Чистая маржа, возраст бизнеса, прокси управления |
| `size` | `ln(revenue)`, `ln(assets)`, `ln(total_equity)` |
| `profitability` | `profit_from_sales / revenue`, `before_tax / revenue`, `net_profit / revenue` |
| `debt_load` | Долг / капитал, чистый долг / прокси EBITDA |
| `debt_service` | `(before_tax + interest_payable) / interest_payable` |
| `liquidity` | Коэффициент текущей ликвидности |
| `cash_flow` | `balance_operating / revenue`, `balance_operating / debt` |

В блоке `debt_load` показатель `profit_from_sales` используется как прокси EBITDA, хотя эти величины не тождественны. Формулу обслуживания долга необходимо интерпретировать с учётом принятого в исходном коде определения `interest_payable`.

### 8.4. Продуктовый скоринг

Расчёт аннуитетного платежа:

$P = A \cdot \frac{r(1+r)^n}{(1+r)^n-1}$

где:

- \(A\) — сумма кредита;
- \(r\) — месячная процентная ставка;
- \(n\) — срок в месяцах.

При нулевой ставке \(P=A/n\).

Факторы продуктового скоринга:

- $s_1=\min(1,\text{fin\_score}/\text{требование продукта})$;
- $s_2=\operatorname{clip}(\text{net\_profit}/P,0,1)$;
- $s_3=\min(1,\text{total\_equity}/\text{сумма продукта})$;
- $s_4=\min(1,\text{age}/\text{минимальный возраст бизнеса})$.

Итог:

${scoring}=100\cdot(0.40s_1+0.20s_2+0.25s_3+0.15s_4)$

## 10. Обработка ошибок и пропусков

Возможные ситуации:

- неизвестный ИНН;
- отсутствие финансовой отчётности;
- отсутствие `product_id` для сценария с конкретным продуктом;
- пустой каталог;
- продукт не найден;
- неполные `fin_params`;
- отсутствие `amount` или `term`;
- недопустимая цель кредита;
- ошибка API;
- нулевой знаменатель финансового коэффициента.

Недоступные показатели исключаются из агрегирования, после чего веса оставшихся показателей нормируются. Нулевой знаменатель обычно приводит к отсутствию соответствующего коэффициента. Финансовый результат содержит `data_quality` и `missing_blocks`.

При ошибке расчёта продукта `has_error=True`, а `employee_rout=True`. По текущему описанию реализация может также помечать продукт ошибкой, если ошибка возникла на этапе подготовки общих данных, даже когда отдельный расчёт продукта завершился успешно.

## 11. Ограничения модели

1. Модель использует один отчётный год; коэффициент вариации выручки исключён, поскольку для него нужно не менее трёх лет.
2. Нет полного анализа динамики, прогноза денежных потоков, качественного интервью и экспертных корректировок, предусмотренных методологией АКРА.
3. Отраслевые `s_otr` являются заглушками.
4. Группировка ОКВЭД может грубо представлять неоднородные отрасли.
5. `profit_from_sales` используется как прокси EBITDA, хотя это не одно и то же.
6. В продуктовом скоринге необходимо проверить периодизацию `net_profit` относительно ежемесячного платежа.
7. Внутренняя буквенная шкала не является официальной рейтинговой шкалой АКРА.

Перед промышленным использованием рекомендуется провести валидацию на исторических дефолтах и погашениях, backtesting, калибровку порогов, проверку стабильности по отраслям и размерам компаний, мониторинг дрейфа данных и версионирование весов.

## 12. Проверки и тестирование

Рекомендуемые модульные тесты:

- шкалирование на нижней, средней и верхней границах;
- обратное шкалирование, когда меньшее значение лучше;
- пропуск показателя и перенормировка весов;
- нулевые и отрицательные знаменатели;
- отсутствие процентильных границ;
- неизвестная отраслевая группа;
- нормализация ручных полей `line_XXXX`;
- аннуитетный платёж при нулевой и положительной ставке;
- фильтрация по категории, цели, сумме и сроку;
- пустой каталог и неполные `fin_params`;
- попадание точно на границы пороговой зоны;
- ошибки API и корректное закрытие соединений.

Интеграционные тесты следует выполнять с подменами `FNSApi` и `InternalApi` для сценариев организации с отчётностью, ИП с ручными данными, неизвестного ИНН, частично доступных блоков и нескольких подходящих продуктов. В тестах необходимо фиксировать версии `weight.json` и `config.py`.
