# Описание структуры БД

## 1. Общая информация

База данных предназначена для прототипа системы кредитования индивидуальных предпринимателей (ИП) и обществ с ограниченной ответственностью (ООО).

База хранит:

- сведения о компаниях-заёмщиках;
    
- финансовые показатели компаний;
    
- доступные кредитные продукты;
    
- поданные кредитные заявки;
    
- результаты проверок и скоринга для разных кредитных продуктов;
    
- итоговые решения по заявкам;
    
- историю обработки заявок;
    
- учётные записи пользователей.
    

Система поддерживает автоматическую проверку первоначально выбранного кредитного продукта. Если он не соответствует требованиям, система проверяет остальные продукты, которые подходили заявителю при предварительном подборе. Каждый фактически проверенный продукт фиксируется отдельной записью в `applications_checks`.

Одобренные альтернативы сохраняются как предложения в `application_offers` и показываются предпринимателю. Предприниматель выбирает одно предложение, после чего заявка финально одобряется на условиях выбранного продукта без повторного скоринга и дополнительных проверок. Если ни одна альтернатива не одобрена, фиксируется отказ.

В сценарии ручной проверки банковский сотрудник может сформировать собственное предложение с суммой и сроком; предприниматель принимает или отклоняет его. Принятое предложение является окончательным одобрением.

Первоначальные параметры заявки сохраняются. Одобренный продукт записывается в `applications_decisions.product_id`, результаты проверок всех рассмотренных продуктов — в `applications_checks`, а предложения — в `application_offers`.

    

## 2. Таблицы и поля

### 2.1. `companies` — компании

Хранит общие сведения о компании-заёмщике.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`inn`|`VARCHAR(12)`|PK, CHECK длины 10 или 12 символов|ИНН компании|
|`company_name`|`VARCHAR(255)`||Название компании (может отсутствовать)|
|`registration_date`|`DATE`||Дата регистрации|
|`company_status`|`VARCHAR(50)`||Статус компании|
|`industry`|`VARCHAR(2)`||Код отрасли (2 символа)|
|`region_code`|`VARCHAR(20)`||Код региона|
|`is_simplified_tax`|`BOOLEAN`||Признак применения УСН|
|`dissolution_flag`|`BOOLEAN`||Признак ликвидации (прекращения деятельности)|

`inn` хранится как строка, поскольку ИНН является идентификатором, а не числовой величиной.

`dissolution_flag` — характеристика компании, полученная из источника данных; обрабатывается отдельным правилом кредитной политики и сам по себе не задаёт результат. `is_simplified_tax` — налоговый режим компании, учитывается правилами проверок и скоринга.

### 2.2. `financial_statements` — финансовая отчётность

Хранит годовые финансовые показатели компании за отчётный год. Одна запись — один отчётный год.

| Поле                | Тип данных                                | Ключ / ограничение   | Описание                                 |
| ------------------- | ----------------------------------------- | -------------------- | ---------------------------------------- |
| `financial_id`      | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | PK                   | Идентификатор финансовой записи          |
| `inn`               | `VARCHAR(12)`                             | FK → `companies.inn` | Компания, к которой относится отчётность |
| `report_year`       | `INTEGER`                                 | CHECK ≥ 1900         | Отчётный год                             |
| `revenue`           | `NUMERIC(18,2)`                           |                      | Выручка                                  |
| `net_profit`        | `NUMERIC(18,2)`                           |                      | Чистая прибыль                           |
| `assets`            | `NUMERIC(18,2)`                           |                      | Общая стоимость активов                  |
| `current_assets`    | `NUMERIC(18,2)`                           |                      | Оборотные активы                         |
| `total_equity`      | `NUMERIC(18,2)`                           |                      | Собственный капитал                      |
| `longterm_debt`     | `NUMERIC(18,2)`                           |                      | Долгосрочный долг                        |
| `shortterm_debt`    | `NUMERIC(18,2)`                           |                      | Краткосрочный долг                       |
| `shortterm_liab`    | `NUMERIC(18,2)`                           |                      | Краткосрочные обязательства              |
| `retained_earnings` | `NUMERIC(18,2)`                           |                      | Нераспределённая прибыль                 |
| `profit_from_sales` | `NUMERIC(18,2)`                           |                      | Прибыль от продаж                        |
| `before_tax`        | `NUMERIC(18,2)`                           |                      | Прибыль до налогообложения               |
| `cash_equivalents`  | `NUMERIC(18,2)`                           |                      | Денежные средства и эквиваленты          |
| `interest_payable`  | `NUMERIC(18,2)`                           |                      | Проценты к уплате                        |
| `balance_operating` | `NUMERIC(18,2)`                           |                      | Показатель операционного баланса         |

Ограничение уникальности `(inn, report_year)` не позволяет добавить несколько записей отчётности одной компании за один отчётный год.

Отчётность годовая: данные вводятся предпринимателем вручную. Динамика показателей рассчитывается по годам; если данных за прошлые годы нет, динамика отсутствует — это не блокирует скоринг, а учитывается в формуле оценки (снижает балл).

#### Расчётные финансовые показатели

На основе сохранённых данных backend может рассчитывать дополнительные коэффициенты:

- Рентабельность по чистой прибыли: `net_profit / revenue`.
    
- Рентабельность продаж: `profit_from_sales / revenue`.
    
- Коэффициент текущей ликвидности: `current_assets / shortterm_liab`.
    
- Коэффициент автономии: `total_equity / assets`.
    
- Долговая нагрузка: `(longterm_debt + shortterm_debt) / assets`.
    
- Доля краткосрочных обязательств в активах: `shortterm_liab / assets`.
    
- Денежное покрытие краткосрочных обязательств: `cash_equivalents / shortterm_liab`.
    
- Процентная нагрузка: `interest_payable / revenue`.
    

Эти коэффициенты являются производными показателями и не требуют обязательного хранения отдельными полями.

При расчёте необходимо учитывать деление на ноль и отсутствие исходных данных. Отсутствующее значение не следует автоматически трактовать как ноль.

### 2.3. `loan_catalog` — каталог кредитных продуктов

Хранит параметры доступных кредитных продуктов и условия, которым должна соответствовать заявка.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`product_id`|`BIGINT GENERATED BY DEFAULT AS IDENTITY`|PK|Идентификатор продукта|
|`product_name`|`VARCHAR(255)`||Название продукта|
|`description`|`TEXT`||Описание продукта|
|`business_category`|`VARCHAR(20)`|CHECK: `ip`, `ooo`, `both`|Категория бизнеса: ИП, ООО или оба типа|
|`min_amount`|`NUMERIC(18,2)`|CHECK ≥ 0|Минимальная сумма кредита|
|`max_amount`|`NUMERIC(18,2)`|CHECK ≥ `min_amount`|Максимальная сумма кредита|
|`min_term_months`|`INTEGER`|CHECK > 0|Минимальный срок кредита в месяцах|
|`max_term_months`|`INTEGER`|CHECK ≥ `min_term_months`|Максимальный срок кредита в месяцах|
|`percent`|`NUMERIC(5,2)`|CHECK ≥ 0|Процентная ставка в год|
|`loan_purpose`|`VARCHAR(50)`||Цель кредитования|
|`is_active`|`BOOLEAN`||Доступен ли продукт|
|`business_age`|`INTEGER`|CHECK ≥ 0|Требуемый возраст бизнеса в месяцах|

Поле `is_active` определяет, может ли продукт участвовать в рассмотрении новых заявок.

Поле `business_age` задаёт минимальный возраст бизнеса (в месяцах), при котором продукт доступен заявителю. Фактический возраст бизнеса рассчитывается по `companies.registration_date`. Если возраст заявителя меньше `business_age`, продукт не считается подходящим.

При поиске альтернатив система должна учитывать активность продукта, категорию бизнеса заявителя, допустимую сумму, срок и остальные обязательные условия.

### 2.4. `loan_applications` — кредитные заявки

Хранит поданные предпринимателями заявки и первоначально выбранные параметры кредита.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`application_id`|`VARCHAR(36)`|PK|Идентификатор заявки, например `APP000001` или UUID|
|`inn`|`VARCHAR(12)`|FK → `companies.inn`|Компания-заявитель|
|`product_id`|`BIGINT`|FK → `loan_catalog.product_id`|Первоначально выбранный продукт|
|`requested_amount`|`NUMERIC(18,2)`|CHECK > 0|Запрашиваемая сумма|
|`requested_term_months`|`INTEGER`|CHECK > 0|Запрашиваемый срок в месяцах|
|`loan_purpose`|`VARCHAR(50)`||Цель кредита, выбранная заявителем|
|`application_status`|`VARCHAR(30)`|CHECK|Текущий статус заявки|
|`created_at`|`TIMESTAMPTZ`||Дата и время подачи заявки|

Допустимые статусы заявки:

- `submitted` — заявка подана;
    
- `processing` — заявка обрабатывается;
    
- `manual_review` — требуется рассмотрение сотрудником;
    
- `offer_pending` — сформировано предложение (одобренная альтернатива или условия сотрудника), ожидается решение предпринимателя;
    
- `approved` — заявка одобрена;
    
- `rejected` — заявка отклонена.
    

`loan_purpose` хранит код выбранной заявителем цели и не является внешним ключом в текущей модели.

#### Сохранение первоначальных параметров

Поле `loan_applications.product_id` содержит продукт, который выбрал пользователь при подаче заявки.

Если этот продукт не подходит, система не заменяет его идентификатор в исходной заявке. Для альтернативного продукта создаётся отдельная запись проверки в `applications_checks` и предложение в `application_offers`, а итоговое одобрение записывается в `applications_decisions` после выбора предпринимателя.

Таким образом, сохраняется информация как о первоначальном выборе пользователя, так и о фактически одобренном продукте.

### 2.5. `applications_checks` — проверки и скоринг

Хранит результаты проверки заявки для конкретных кредитных продуктов.

Одна заявка может иметь несколько записей в этой таблице — по одной для каждого проверенного продукта. Все эти записи относятся к одной исходной заявке, но могут содержать разные значения `product_id`.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`check_id`|`BIGINT GENERATED BY DEFAULT AS IDENTITY`|PK|Идентификатор проверки|
|`application_id`|`VARCHAR(36)`|FK → `loan_applications.application_id`|Проверяемая заявка|
|`product_id`|`BIGINT`|FK → `loan_catalog.product_id`|Проверяемый кредитный продукт|
|`has_error`|`BOOLEAN`||Есть ли ошибки или противоречия в данных|
|`risk_category`|`VARCHAR(30)`||Категория риска|
|`scoring`|`INTEGER`||Итоговый скоринговый балл|
|`scoring_factors`|`JSONB`||Факторы, повлиявшие на оценку|
|`employee_rout`|`BOOLEAN`||Требуется ли передать заявку сотруднику|
|`routing_reason`|`TEXT`||Причина выбора маршрута проверки|
|`checked_at`|`TIMESTAMPTZ`||Дата и время проверки|

На одну пару `(application_id, product_id)` допускается одна запись проверки; повторная проверка того же продукта обновляет существующую запись.

#### Логика проверки продуктов

1. Система получает исходную заявку из `loan_applications`.
    
2. Проверяет первоначально выбранный продукт.
    
3. Если продукт проходит все обязательные проверки, он может быть одобрен.
    
4. Если первоначальный продукт не проходит проверку, система рассматривает другие активные продукты, подходящие для категории бизнеса заявителя.
    
5. Для каждого фактически проверенного продукта создаётся отдельная запись в `applications_checks`.
    
6. При проверке альтернатив используются исходные сумма, срок и цель кредита. Продукт, не соответствующий этим параметрам или другим обязательным требованиям, не считается подходящим.
    
7. Если подходящий продукт найден, система записывает итоговое решение в `applications_decisions`.
    
8. Если ни один продукт не подходит, система фиксирует отказ.
    

Поле `scoring` не является единственным условием одобрения. Решение должно учитывать обязательные проверки, допустимые параметры продукта и правила кредитной политики.

Если для конкретной проверки требуется участие сотрудника, это отражается через `employee_rout`. Поведение при передаче на ручное рассмотрение должно определяться бизнес-логикой системы.

Поле `product_id` в этой таблице указывает именно на продукт, который проверялся в соответствующей записи.

### 2.6. `applications_decisions` — решения по заявкам

Хранит итоговые решения системы или банковского сотрудника.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`decision_id`|`BIGINT GENERATED BY DEFAULT AS IDENTITY`|PK|Идентификатор решения|
|`application_id`|`VARCHAR(36)`|FK → `loan_applications.application_id`|Заявка, по которой принято решение|
|`product_id`|`BIGINT`|FK → `loan_catalog.product_id`, допускает NULL|Продукт, по которому принято решение|
|`offer_id`|`BIGINT`|FK → `application_offers.offer_id`, допускает NULL|Предложение, на основании которого принято решение|
|`decision_type`|`VARCHAR(30)`|CHECK: `approved`, `rejected`|Результат рассмотрения|
|`decision_source`|`VARCHAR(30)`|CHECK: `automatic`, `bank_employee`|Источник решения|
|`decided_by`|`VARCHAR(100)`|FK → `login.username`, обязателен для `bank_employee`|Сотрудник, принявший решение|
|`decision_reason`|`TEXT`||Обоснование решения|
|`approved_amount`|`NUMERIC(18,2)`|CHECK ≥ 0, допускает NULL|Одобренная сумма|
|`approved_term_months`|`INTEGER`|CHECK > 0, допускает NULL|Одобренный срок|
|`decided_at`|`TIMESTAMPTZ`||Дата и время принятия решения|

#### Назначение `product_id`

Поле `product_id` определяет, какой именно кредитный продукт был одобрен или рассматривался в итоговом решении.

Это поле ссылается на `loan_catalog.product_id`.

Если пользователь выбрал продукт № 1, но он не прошёл проверку, а продукт № 2 прошёл все обязательные проверки и был выбран предпринимателем, в `applications_decisions` сохраняется решение с `product_id = 2` и `offer_id` соответствующего предложения.

Пример записи:

|Поле|Значение|
|---|---|
|`application_id`|`APP000001`|
|`product_id`|`2`|
|`offer_id`|`1`|
|`decision_type`|`approved`|
|`decision_source`|`automatic`|
|`decision_reason`|`Первоначальный продукт не прошёл проверку; альтернативный продукт 2 одобрен и выбран предпринимателем`|
|`approved_amount`|`1500000.00`|
|`approved_term_months`|`12`|

Это иллюстративный пример, а не предопределённые условия кредитования.

Одобренная сумма и срок должны соответствовать условиям продукта и результатам проверки. Если исходные параметры не подходят альтернативному продукту, такой продукт нельзя автоматически одобрять на тех же условиях.

#### Связь с предложениями

Если итоговое решение принято на основании выбранного предпринимателем предложения, поле `offer_id` указывает на соответствующую запись в `application_offers` (§2.9). Для решений, принятых сотрудником, поле `decided_by` содержит имя пользователя из `login`; для автоматических решений оно не заполняется.

Итоговым считается наиболее позднее решение по заявке (по `decided_at` и `decision_id`).

#### Допустимые решения

- `approved` — продукт одобрен;
    
- `rejected` — заявка отклонена, поскольку подходящий продукт не найден либо принято решение об отказе.
    

Состояние «предложено, ожидается выбор» не является решением: предложения хранятся в `application_offers` (§2.9), а в `applications_decisions` фиксируется только итоговое решение. Если заявка пересматривалась, актуальным считается наиболее позднее решение.

#### Несколько решений по одной заявке

Таблица допускает несколько решений по одной заявке, чтобы поддерживать повторное рассмотрение или изменение ранее принятого решения.

Backend должен однозначно определять актуальное решение. Например, для этого можно использовать наиболее позднюю запись по `decided_at` и `decision_id`.

Если система должна хранить только одно итоговое решение на заявку, это ограничение можно добавить отдельно после определения правил повторного рассмотрения.

### 2.7. `applications_history` — история обработки

Хранит события обработки заявки и изменения её статуса.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`history_id`|`BIGINT GENERATED BY DEFAULT AS IDENTITY`|PK|Идентификатор события|
|`application_id`|`VARCHAR(36)`|FK → `loan_applications.application_id`|Заявка, к которой относится событие|
|`event_type`|`VARCHAR(50)`|CHECK по словарю событий|Тип события|
|`actor_username`|`VARCHAR(100)`|FK → `login.username`, допускает NULL|Пользователь, выполнивший действие (NULL для системных событий)|
|`old_status`|`VARCHAR(30)`|Допускает NULL|Предыдущий статус|
|`new_status`|`VARCHAR(30)`|Допускает NULL|Новый статус|
|`event_description`|`TEXT`||Описание события|
|`created_at`|`TIMESTAMPTZ`||Дата и время события|

При изменении статуса заявки backend должен записывать соответствующее событие в историю.

Допустимые значения `event_type`: `application_submitted`, `processing_started`, `product_checked`, `scoring_calculated`, `manual_review_assigned`, `offer_created`, `offer_selected`, `offer_declined`, `decision_made`, `status_changed`. Поле `actor_username` заполняется для действий пользователя (подача заявки, выбор или отклонение предложения, решение сотрудника) и остаётся пустым для системных событий.

Например, история может содержать события:

- подача заявки;
    
- начало автоматической проверки;
    
- проверка первоначального продукта;
    
- проверка альтернативного продукта;
    
- автоматическое одобрение продукта;
    
- отказ по результатам проверки;
    
- передача на ручное рассмотрение;
    
- принятие решения сотрудником.
    

При автоматическом одобрении в истории следует отразить, какой продукт был одобрен и почему первоначально выбранный продукт не был использован.

При отказе история должна содержать причину, доступную для аудита и последующего анализа.

Таблица истории не заменяет таблицу решений: в `applications_decisions` хранится само решение, а в `applications_history` — последовательность событий обработки заявки.

### 2.8. `login` — учётные записи

Хранит учётные записи пользователей системы.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`username`|`VARCHAR(100)`|PK|Имя пользователя|
|`password`|`TEXT`|NOT NULL|Хеш пароля, а не пароль в открытом виде|
|`profile_type`|`VARCHAR(20)`|CHECK: `business`, `employee`|Тип профиля: бизнес или сотрудник|
|`company_inn`|`VARCHAR(12)`|FK → `companies.inn`, обязателен для `business`|Компания, к которой привязан бизнес-пользователь|

Поле `company_inn` связывает бизнес-пользователя с компанией: для `profile_type = 'business'` оно обязательно, для `employee` — пусто. Благодаря этой связи предприниматель видит только заявки своей компании (US-01, US-07).

Для аудита действий сотрудника используется `applications_decisions.decided_by`, `application_offers.created_by` и `applications_history.actor_username`; все три поля ссылаются на `login.username`.

### 2.9. `application_offers` — предложения по заявке

Хранит предложения, сформированные системой или банковским сотрудником. Предложение становится финальным одобрением после того, как предприниматель его выбрал.

|Поле|Тип данных|Ключ / ограничение|Описание|
|---|---|---|---|
|`offer_id`|`BIGINT GENERATED BY DEFAULT AS IDENTITY`|PK|Идентификатор предложения|
|`application_id`|`VARCHAR(36)`|FK → `loan_applications.application_id`|Заявка, по которой сформировано предложение|
|`product_id`|`BIGINT`|FK → `loan_catalog.product_id`|Предлагаемый кредитный продукт|
|`approved_amount`|`NUMERIC(18,2)`|CHECK > 0|Предлагаемая сумма|
|`approved_term_months`|`INTEGER`|CHECK > 0|Предлагаемый срок в месяцах|
|`offer_source`|`VARCHAR(30)`|CHECK: `automatic`, `bank_employee`|Кто сформировал предложение|
|`created_by`|`VARCHAR(100)`|FK → `login.username`; обязателен для `bank_employee`|Сотрудник, создавший предложение|
|`offer_status`|`VARCHAR(30)`|CHECK: `offered`, `selected`, `declined`, `superseded`|Статус предложения|
|`created_at`|`TIMESTAMPTZ`||Дата и время формирования предложения|
|`decided_at`|`TIMESTAMPTZ`|NULL только для `offered`|Дата и время решения по предложению|

Статусы предложения:

- `offered` — предложение активно, ожидается решение предпринимателя;
- `selected` — предприниматель выбрал предложение;
- `declined` — предприниматель отклонил предложение;
- `superseded` — предложение закрыто, потому что предприниматель выбрал другое.

Правила:

1. По одной заявке допускается только одно выбранное предложение — это обеспечивается частичным уникальным индексом.
2. Автоматические предложения формируются только из продуктов, прошедших обязательные проверки: отдельный скоринг при выборе не выполняется.
3. Предложение сотрудника содержит сумму и срок, выбранные сотрудником; они окончательны и системой не оспариваются.
4. Если предприниматель отклонил предложение сотрудника, заявка фиксируется как `rejected` с причиной «предприниматель отклонил предложение».
5. Выбор предложения отражается в `applications_decisions` как итоговое решение со ссылкой на `offer_id`, а также событиями `offer_selected` / `offer_declined` в истории.

### Назначение связей при альтернативном одобрении

- `loan_applications.product_id` хранит первоначально выбранный продукт.
    
- `applications_checks.product_id` хранит продукт, проверенный в рамках конкретной проверки.
    
- `applications_decisions.product_id` хранит продукт, указанный в итоговом решении.
    

Эти поля имеют разные назначения. Поэтому при одобрении альтернативы не нужно перезаписывать `loan_applications.product_id`: первоначальный выбор остаётся в заявке, одобренный продукт — в решении, а предложенные варианты — в `application_offers`.

## 4. Общие правила целостности

1. ИНН хранится как строка, а не число.
    
2. Для каждой таблицы определён первичный ключ.
    
3. Внешние ключи не позволяют ссылаться на отсутствующую компанию, заявку или кредитный продукт.
    
4. Отчётность хранится в годовом разрезе: одна запись на компанию за отчётный год.
    
5. Максимальная сумма и срок продукта не могут быть меньше минимальных.
    
6. Сумма заявки и запрашиваемый срок должны быть положительными.
    
7. Одобренная сумма не может быть отрицательной.
    
8. Одобренный срок должен быть положительным.
    
9. Значения флагов хранятся как `BOOLEAN`.
    
10. Пароли должны храниться только в виде безопасных хешей.
    
11. В `financial_statements` запрещены дубли одной компании за один и тот же отчётный год.
    
12. `applications_checks.product_id` указывает на продукт, проверенный в конкретной записи.
    
13. `applications_decisions.product_id` указывает на продукт, указанный в решении.
    
14. Для решения `approved` должны быть указаны одобренный продукт, сумма и срок.
    
15. Для решения `rejected` одобренный продукт и одобренные параметры могут отсутствовать.
    
16. Статус заявки должен соответствовать допустимым значениям, определённым в модели.
17. Учётная запись `business` должна быть связана с существующей компанией через `login.company_inn`; у `employee` это поле пустое.
18. Решение с `decision_source = 'bank_employee'` должно содержать имя сотрудника в `decided_by`.
19. Для предложения с `offer_source = 'bank_employee'` должен быть указан автор в `created_by`.
20. Сумма и срок предложения должны быть положительными.
21. По одной заявке допускается только одно выбранное предложение.
22. Для одобрения по выбранному предложению `applications_decisions.offer_id` указывает на это предложение.
23. Значение `event_type` в истории ограничено словарём допустимых событий.
    

## 5. Логика автоматической обработки заявки

### 5.1. Первоначальная проверка

После подачи заявки система сохраняет её первоначальные параметры в `loan_applications`.

Затем проверяется первоначально выбранный продукт.

Результат проверки сохраняется в `applications_checks`.

### 5.2. Проверка альтернативных продуктов

Если первоначально выбранный продукт не прошёл обязательные проверки, система рассматривает остальные продукты, которые подходили заявителю при предварительном подборе (категория бизнеса, сумма, срок, цель, `business_age`), кроме уже проверенного. Для каждого проверенного продукта создаётся отдельная запись в `applications_checks`, для каждого одобренного — предложение в `application_offers`.

Для каждого продукта проверяется:

- соответствует ли продукт категории бизнеса заявителя;
    
- попадают ли запрошенная сумма и срок в допустимые границы продукта;
    
- соответствует ли цель кредита требованиям продукта;
    
- пройдены ли остальные обязательные проверки;
    
- отсутствуют ли блокирующие ошибки;
    
- допускает ли кредитная политика автоматическое одобрение.
    

Исходные сумма, срок и цель берутся из `loan_applications`. Если параметры не соответствуют требованиям альтернативного продукта, он не должен считаться одобренным на этих условиях.

### 5.3. Формирование предложений и выбор предпринимателя

Если первоначально выбранный продукт прошёл все обязательные проверки, система автоматически одобряет его сразу, без предложений.

Если первоначальный продукт не прошёл проверку, система проверяет остальные продукты, которые подходили заявителю при предварительном подборе, и для каждого одобренного продукта создаёт запись в `application_offers` со статусом `offered`. Заявка переводится в статус `offer_pending`.

Если одобрена одна или несколько альтернатив, предприниматель выбирает одно предложение. Выбранное предложение получает статус `selected`, остальные — `superseded`. Повторный скоринг и дополнительные проверки не выполняются: продукты уже одобрены системой.

Если ни один альтернативный продукт не прошёл проверки, система фиксирует отказ.

### 5.4. Сохранение решения

При одобрении по выбранному предложению система создаёт запись в `applications_decisions` со следующими данными:

- `application_id` — исходная заявка;
    
- `product_id` — фактически одобренный продукт;
    
- `offer_id` — выбранное предпринимателем предложение;
    
- `decision_type = 'approved'`;
    
- `decision_source` — `automatic` (система) или `bank_employee` (сотрудник);
    
- `decided_by` — сотрудник, принявший решение (только для `bank_employee`);
    
- `decision_reason` — обоснование решения;
    
- `approved_amount` — одобренная сумма;
    
- `approved_term_months` — одобренный срок;
    
- `decided_at` — время принятия решения.
    

После этого `loan_applications.application_status` обновляется на `approved`, предложение получает статус `selected`, остальные предложения — `superseded`, а в `applications_history` записываются события `offer_selected` и `decision_made`.

Если ни один продукт не проходит все обязательные проверки, создаётся решение `rejected`, статус заявки обновляется на `rejected`, а причина фиксируется в решении и истории. Предложения в этом случае не формируются.

### 5.5. Ручное рассмотрение

Если проверка выявила обстоятельства, требующие участия сотрудника, система устанавливает `employee_rout = TRUE` и переводит заявку в `manual_review`; причина сохраняется в `applications_checks.routing_reason`.

Для заявки, переданной на ручную проверку, автоматический поиск альтернатив не выполняется — решение принимает сотрудник. Сотрудник может одобрить заявку, отказать или сформировать предложение с собственной суммой и сроком (§5.6).

Заявка не может одновременно считаться окончательно одобренной и ожидающей ручного решения.

### 5.6. Ручное рассмотрение и предложение условий сотрудником
 
	- Сотрудник открывает заявку в личном кабинете.
	- Самостоятельно принимает решение `approved` или `rejected`.
	- **Система не запускает дополнительные проверки перед исполнением этого решения.**
	- При одобрении сотрудник указывает одобряемую сумму и срок; они окончательны и не могут быть оспорены системой.
	- При необходимости сотрудник формирует предложение (`application_offers`, `offer_source = 'bank_employee'`) с собственной суммой и сроком; оно направляется предпринимателю.
	- Предприниматель принимает или отклоняет предложение. При принятии заявка переводится в `approved`, при отклонении — в `rejected` с причиной «предприниматель отклонил предложение»; события записываются в `applications_history`.
	
	Решение сотрудника является окончательным: система не перепроверяет его и не отклоняет автоматически из-за низкого скоринга или непрохождения обычных автоматических проверок. Решение сохраняется с `decision_source = 'bank_employee'` и `decided_by` — логином сотрудника.

## 6. Архитектурные особенности и ограничения

1. `login.company_inn` связывает бизнес-пользователя с компанией; `decided_by`, `created_by` и `actor_username` идентифицируют сотрудника.
    
2. `loan_applications.product_id` хранит первоначальный выбор пользователя, а `applications_decisions.product_id` — продукт, указанный в итоговом решении.
    
3. `applications_checks` может содержать несколько проверок одной заявки для разных продуктов.
    
4. `applications_decisions` может содержать несколько решений одной заявки. Актуальное решение должно определяться бизнес-логикой.
    
5. Альтернативы и условия сотрудника хранятся в `application_offers`; состояние ожидания решения предпринимателя — статус заявки `offer_pending`.
    
6. Внешние ключи обеспечивают ссылочную целостность, но сами по себе не гарантируют, что одобренный продукт успешно прошёл все проверки.
    
7. Backend обязан проверять, что продукт, указанный в решении `approved`, соответствует результатам проверок и условиям кредитной политики, а при решении по предложению — что предложение выбрано предпринимателем.
    
8. При нескольких одобренных предложениях выбор делает предприниматель; backend фиксирует выбранное предложение и не перепроверяет его.
    
9. Расчёт финансовых коэффициентов должен учитывать нулевые знаменатели и отсутствующие данные.
    
10. Правила скоринга, маршрутизации и автоматического одобрения реализуются в коде и не хранятся в БД; правила ручного рассмотрения и повторного принятия решений определяются бизнес-логикой.
