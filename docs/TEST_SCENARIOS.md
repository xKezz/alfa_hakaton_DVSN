# Тестовые сценарии

## Тестовые данные и доступы

`src/db/setup_db.py` создаёт 4 компании, 11 продуктов и 6 учётных записей.
Полный синтетический набор: `src/db/df_companies.csv` и
`src/db/df_financial.csv` (по 127 828 записей).

| Логин | Пароль | Роль |
|---|---|---|
| `client` | `client` | предприниматель |
| `login1`…`login4` | `login1`…`login4` | предприниматели |
| `bank` | `bank` | сотрудник банка |

## E2E-1: ручная проверка → предложение сотрудника → принятие

1. Запустить приложение (`docker compose up --build -d` или локально).
2. Войти как `client / client`.
3. Создать заявку с целью «Другое»; ожидаемый статус — `manual_review`.
4. Войти как `bank / bank`, открыть заявку в очереди.
5. Создать предложение (`product_id`, сумма, срок, обоснование);
   ожидаемый статус заявки — `offer_pending`, оффер — `offered`.
6. Войти как `client / client`, открыть заявку, принять предложение.
7. Ожидаемый результат: заявка `approved`, оффер `selected`, решение
   `decision_source=bank_employee`, `decided_by=bank`, сумма/срок из оффера.

## E2E-2: отказ предпринимателя

1. Повторить шаги 1–5 E2E-1.
2. Предприниматель отклоняет единственный оффер.
3. Ожидаемый результат: оффер `declined`, заявка `rejected`, причина
   «Предприниматель отклонил предложение»; повторное действие — `409`.

## E2E-3: автоматический скоринг

1. Войти как `client / client`.
2. Выбрать продукт с подходящими параметрами и стандартную цель.
3. Ожидаемый результат: автоматическое `approved`/`rejected` без ручной
   проверки; решение сохранено в `applications_decisions`.

## Негативные проверки

- запрос без `Authorization` → `401`;
- предприниматель обращается к чужой заявке → `403`;
- предприниматель вызывает эндпоинт сотрудника → `403`;
- повторный выбор/отклонение оффера → `409`;
- невалидные сумма/срок/ИНН/цель → `422`;
- отсутствующая компания/продукт/заявка → `404`.

выбор/отклонение оффера, доступ к чужим заявкам и повторные действия.
Подробный ручной сценарий с SQL-проверками — в корневом `README.md`.
